## 🔴 ١. ثغرة أمنية حرجة — أُصلحت وأُثبتت

### ما وجدته

ملف `.htaccess` المرفق في حزمة النشر يبدأ بقاعدة تخدم **أي ملف موجود على القرص مباشرةً**:

```apache
RewriteCond %{REQUEST_FILENAME} -f [OR]     # ← تسبق قاعدة /api/
RewriteCond %{REQUEST_FILENAME} -d
RewriteRule ^ - [L]                           # ← تخدم الملف بلا PHP
```

وقاعدة `/api/` تأتي **بعدها**، فلا تُطبَّق على الملفات الحقيقية. النتيجة أن هذه المسارات كانت متاحة لأي زائر على الإنترنت:

| المسار | ما يحدث |
|---|---|
| `/api/storage/secret.key` | 🔴 تسريب مفتاح توقيع الجلسات |
| `/api/storage/app.sqlite` | 🔴 تسريب قاعدة البيانات كاملة (هاشات كلمات المرور) |
| `/api/seed.php` | 🔴 **يمحو قاعدة البيانات** — بلا أي مصادقة |
| `/api/install.php?confirm=yes` | 🔴 **يمحو قاعدة البيانات** — بكلمة «confirm» فقط، وهي ليست حماية |

### الإثبات العملي (نُفِّذ فعلاً على الخادم)

محاكاة سلوك Apache على منفذ منفصل:

```
  /api/storage/app.sqlite  → HTTP 200  548,864 بايت
  /api/storage/secret.key  → HTTP 200  64 بايت
  app.sqlite magic         → S Q L i t e   f o r m a t   3
```

ثم تزوير جلسة مدير باستخدام المفتاح المسروق — **دون أي كلمة مرور**:

```
  /api/auth/me       → HTTP 200  {"ok":true,"user":{"id":33,...,"role":"admin"}}
  /api/admin/stats   → HTTP 200  (بيانات لوحة الإدارة كاملة)
```

أي أن أي مهاجم يستطيع **الاستيلاء الكامل على الموقع** أو **محو كل بياناته**.

### الإصلاح — ثلاث طبقات

| الطبقة | الملف | يعمل على |
|---|---|---|
| ① منع مجلد التخزين | `api/storage/.htaccess` **(جديد)** | Apache · LiteSpeed |
| ② قواعد منع تسبق خدمة الملفات | `.htaccess` الجذري (مُعدَّل) | Apache · LiteSpeed |
| ③ بوابة PHP لسكربتات الصيانة | `api/includes/maintenance.php` **(جديد)** | **أي خادم — بما فيه Nginx** |

الطبقة ③ هي الأهم لأن Nginx لا يقرأ `.htaccess` إطلاقاً:
- من الطرفية (CLI) → مسموح دائماً
- عبر الويب ويوجد مدير → يلزم رمز مدير صالح
- عبر الويب ولا يوجد مدير (تثبيت أول) → مسموح — لا شيء لنُفقده

### التحقق بعد الإصلاح

```
── سكربتات الصيانة ──
  seed.php                → HTTP 403  "هذا السكربت محمي..."
  install.php?confirm=yes → HTTP 403
  migrate_fields.php      → HTTP 403
  set_password.php        → HTTP 403  "تعمل من الطرفية فقط"

── CLI ما زال يعمل ──
  php api/set_password.php --list  → ✅ يعرض الحسابات
```

### ما زال مطلوباً منك ⚠️

> **إن كان موقعك `t3lam.site/dalel` منشوراً الآن، فالمفتاح وقاعدة البيانات قد يكونان مسرَّبين فعلاً.**

1. ارفع الملفات المصححة.
2. **بدّل `secret.key`** (يُسجّل خروج الجميع — وهذا مقصود، فهو يُبطل أي جلسة مزوَّرة).
3. **غيّر كلمة مرور المدير** عبر `php api/set_password.php <رقم الهاتف>`.
4. افتح `check.html` على موقعك للتأكد — الصفحة تفحص السرية الآن وتعرض تحذيراً أحمر إن بقيت الثغرة.

### 📦 ٢. قاعدة البيانات — اعتماد الأحدث (مؤكَّد من صاحب المشروع)

> **قرار صاحب المشروع:** «القديمة التي فيها أكثر من ٥٠٠ خدمة فهي قديمة **وتم التعديل عليها**،
> لذلك اعتمد الجديدة التي فيها محافظة ديرالزور وحوالي ٣٠٠ خدمة وأكثر.»
>
> فالنسخة ذات العدد الأكبر **مهجورة**، والعدد الأكبر لا يعني أنها الأصحّ.

### ما نُفِّذ

| الخطوة | التفصيل |
|---|---|
| ترقية النسخة الأحدث | `app.sqlite` (الجذر) → `winfeen/api/storage/app.sqlite` |
| أرشفة النسخ القديمة | → `_data-archive/deprecated/` مع ملف توضيحي |
| حذف أداة الدمج | لأنها كانت ستنقل بيانات مهجورة |
| إزالة التكرار | حُذفت نسختان مكرّرتان ٥٤٨ كيلوبايت لكل منهما |

### تنظيف أجريته على القاعدة المؤرشفة

كنت قد لوّثتها بأثناء اختباري، فأعدتها إلى حالتها الأصلية:
- حُذفت ٦ صفوف من `activity_log` نتجت عن تسجيلات دخولي وتجارب البوابة → عادت إلى ١٧٣ (مطابقة تماماً للنسخة المرجعية)
- حُذف صف حالة **يتيم** يشير إلى خدمة محذوفة (`service_status`: ٥٢٤ → ٥٢٣)

### النتيجة الحالية

```
  اسم الموقع   = دليل الدير
  الأقسام      = ٥  (صيدليات · أطباء · كازيات · سرافيس · المخابر)
  المحافظات    = ٢  (حلب · ديرالزور)
  المناطق      = ١٥٨
  الخدمات      = ٣٩٢  (صيدليات ٢٤٢ · أطباء ١٥٠)
  الحقول الديناميكية = ٥ حقول · ٣٤ خياراً
  تعمل الآن    = ٥٧   |   مناوبة = ٣٤
```

### ✅ لا دمج — البيانات القديمة مهجورة بقرار صاحب المشروع

بنيت أداة دمج مُختبرة (تُعيد ١٣١ خدمة ناقصة)، ثم **حُذفت** بعد توضيحك:

> «القديمة التي فيها أكثر من ٥٠٠ خدمة فهي قديمة **وتم التعديل عليها**»

فالعدد الأكبر ليس دليلاً على الأصح. نُقلت القواعد المهجورة إلى `_data-archive/deprecated/`
مع ملف توضيحي، ولم يُدمج منها شيء.

**حُذفت الأداة** تحديداً لأن بقاءها كان يُغري بنقل بيانات مهجورة — وهو ما نبّهتَ ضده.

### 📌 حالة القاعدة المعتمدة — تفصيل مهم

```
المحافظات
  # 1  حلب        ← ٧٢ منطقة (مدن)      ·  ٣٩٢ خدمة
  #10  ديرالزور   ← ٨٦ منطقة (٢٥ مدينة + ٥٩ ريفية + ٢ قرية) ·  ٠ خدمة
```

| القسم | الخدمات | ملاحظة |
|---|---|---|
| صيدليات بشرية | ٢٤٢ | كلها في حلب |
| عيادات أطباء | ١٥٠ | كلها في حلب |
| كازيات | ٠ | — |
| سرفيس واسعافية | ٠ | — |
| المخابر | ٠ | — |

**القراءة:** هيكل ديرالزور جاهز (المحافظة + ٨٦ منطقة) لكن **بلا خدمات بعد**.
والأقسام الثلاثة الأخيرة فارغة في كل المحافظات.

`settings.tagline` ما زال يقول «…في مدينة حلب…» و`settings.city` فارغ — يُضبطان من لوحة الإدارة.

### 🔑 تنبيه: كلمة مرور المدير في النسخة المعتمدة

النسخة المعتمدة فيها حسابان، وكلمة مرور المدير **غير معروفة** (اختبرت ١٠ كلمات شائعة — لم تُطابق أياً منها).

**الحلول:**
```bash
php api/set_password.php --list              # اعرض الحسابات
php api/set_password.php 0936651837          # يولّد كلمة قوية ويطبعها
php api/set_password.php 0936651837 "MyPass" # أو حدّدها بنفسك
```
> الأداة الجديدة `api/set_password.php` ترفض العمل عبر المتصفح نهائياً، وتتحقق من الكلمة فعلياً بعد الحفظ.

## 📱 ٣. تطبيق أندرويد — استُبدل المجلد المشوّه

### المشكلة التي كانت

مجلد `dalel_android/android/` كان **مشوّه البنية** — ملفان في مسارات خاطئة تمنع البناء تماماً:

| المسار الخاطئ | المسار الصحيح |
|---|---|
| `android/app/src/build.gradle` | `android/app/build.gradle` |
| `android/app/src/main/res/AndroidManifest.xml` | `android/app/src/main/AndroidManifest.xml` |
| ❌ مفقود | `android/app/src/main/res/drawable/launch_background.xml` |

`Gradle` لا يجد سكربت بناء وحدة `app`، و`AndroidManifest.xml` داخل `res/` غير صالح أصلاً.

### ما نُفِّذ

استُبدل المجلد بالكامل بخيارك — النسخة السليمة من `dalel-android-flutter.zip`.

**قبل الاستبدال تحقّقت أنه لا فقدان:**

```
  ملفات في الأرشيف : 73
  ملفات في المجلد  : 73
  فروق القائمة     : ✅ نفس الملفات بالضبط
  فروق المحتوى     : 0  → مطابق بايت-ببايت
```

فكل ملفات `lib/` و`test/` و`pubspec.yaml` كانت أصلاً مطابقة؛ المشكلة كانت في قشرة Android وحدها.

## 🧩 ٦. استكمال نظام الحقول الديناميكية

كان النظام مبنيّاً لكن **غير مكتمل**: ١٦ مفتاح بيانات حقيقية في قاعدة البيانات
بلا تعريف مقابل، فلا تظهر ولا تُدار من لوحة الإدارة.

### المشكلة الأولى: مخطط ينكسر على قاعدة قديمة

جدولا `category_fields` و`category_field_options` كانا يُنشآن في `install.php`
و`migrate_fields.php` **فقط** — و`includes/db.php` لا يذكرهما إطلاقاً.
نشر الكود على قاعدة قديمة أو استعادة نسخة احتياطية سابقة ← `/api/meta` يسقط بخطأ SQL.

**الإصلاح:** `db.php` صار يُنشئهما بـ`CREATE TABLE IF NOT EXISTS` مع ترقية
تقدّمية للأعمدة الجديدة. المخطط يُصلح نفسه مع كل طلب — لا حاجة لتشغيل سكربت.
*مُثبَت:* قاعدة اصطناعية بلا الجدولين ← `/api/meta` نجح بعد الطلب الأول.

### المشكلة الثانية: ٤٢ خدمة محجوبة

`api_services()` كان يقصّ النتائج عند `min(200, limit)`. قسم الصيدليات فيه
**٢٤٢** خدمة، بينما بطاقات المناطق تُحسب على العدد الكامل — فتبدو مناطق فيها
خدمات ولا يظهر فيها شيء عند اختيارها. السقف الآن ٥٠٠، والواجهة تجلب بقية
الصفحات إن تجاوز العددُ السقف.

### المشكلة الثالثة: «قابل للفلترة» بلا أثر

العلم يُحفظ في قاعدة البيانات ولا يُقرأ في أي مكان في الواجهة. أُضيف مكوّن
`FieldFilters` يبني شريط فلترة من تعريفات القسم نفسها.

**ثم بطلب منك أُلغيت الفلاتر المنطقية** (دوام ٢٤ ساعة · التوصيل · بنزين · مازوت):
كانت تُنتج شريحة «متوفر» لكل حقل نعم/لا وهي غير مفيدة. أُزيلت من ثلاثة مواضع
حتى لا تعود: البيانات (`filterable = 0`)، ومكوّن العرض، وخيار لوحة الإدارة
(لا يظهر إلا لحقول القائمة، ويُلغى تلقائيًا عند تحويل حقل إلى «نعم/لا»).

**الفلاتر المفعَّلة الآن (٣):** الاختصاص (٢٠) · اتجاه السفر (١٠) · نوع المركبة (٣).
والحقول المنطقية تبقى معروضة في البطاقات كما هي.

### المشكلة الرابعة: الإيموجي تختفي بصمت

أيقونات خيارات الحقول إيموجي (`🤰` للنسائية، `🥗` للتغذية)، ومكوّن `Lucide`
يُرجع `null` لأي اسم لا يعرفه — فتُرسم الأيقونة فراغاً بلا تحذير. صار يرسم
أي نص غير لاتيني كما هو، مع نمط CSS مخصّص.

### المشكلة الخامسة: مُعرّف رقمي يُعرض للمستخدم

إن حُذف اختصاص من القائمة وبقيت قيمة رقمية في `meta`، كان الخادم يعرض الرقم
الخام (`9`) بدل اسم الاختصاص. صار يُسقط القيمة الرقمية غير المطابقة بدل عرضها.

> **مثل هذا في التطبيق:** حارس في `section_screen.dart` كان `r'^\d+\$'` —
> يطابق رقماً متبوعاً بعلامة `$` حرفية، فتمرّ الأرقام الخام رغم الحماية.
> صُحّح إلى `r'^\d+$'`.

### الحقول المعرَّفة الآن (١٤ حقلاً · ٥ أقسام)

| القسم | الحقول | حالة البيانات |
|---|---|---|
| صيدليات (٢٤٢) | الصيدلاني · دوام ٢٤ ساعة · التوصيل | ٢٣٩ خدمة × ٣ قيم — تظهر كلها ✅ |
| أطباء (١٥٠) | الاختصاص (٢٠ خياراً) · سعر المعاينة (ل.س) · المستشفى | ١٥٠ خدمة — كلها ✅ |

## 🗑️ ٧. حذف الطلبات من لوحة التحكم

تبويب «الطلبات» كان يوفّر **موافقة** و**رفضاً** فقط — بلا أي وسيلة للتخلص
من طلب. الخادم كان يملك المسار منذ البداية (`DELETE /api/admin/requests/{id}`)
وواجهة `deleteRequest` مكتوبة في `api.ts` لكنها **غير مستدعاة في أي مكان**.
أُضيف الزر.

⚠️ **تحذير مقصود في التأكيد:** الطلب الموافَق عليه يُنشئ خدمة فعلية، وحذف
الطلب **لا يحذفها**. بدون تنبيه قد يظن المدير أنه أزال المحتوى فتبقى الخدمة
منشورة. لذلك:

- الطلب **غير** الموافَق: تأكيد بسيط
- الطلب الموافَق: التأكيد يذكر رقم الخدمة صراحةً ويوجّه إلى تبويب الخدمات
- أُضيف **رابط مباشر** للخدمة المنشأة في صف الطلب — بدونه كان المدير يرى
  «موافق» ولا يعرف أي خدمة نتجت عنها

**إصلاح مصاحب:** حذف طلب غير موجود كان يردّ «تم حذف الطلب» (تأكيد كاذب عند
النقر المزدوج أو قائمة قديمة). صار يردّ `404 — الطلب غير موجود`.

## 🎛️ ١٠. ميزة الفلاتر — من كود ثابت إلى بيانات يديرها المدير

**الطلب:** «في صفحة الفلاتر يتم إنشاء فلاتر مثل المناطق، وفي القسم المحدد أقوم باختيار الفلتر لعرض الخدمات على أساسه — مثل قسم الصيدليات أختار فلتر المناطق، وفي عيادات الأطباء فلتر الاختصاص، وفي سرافيس واسعافية فلتر نوع المركبة».

**الوضع قبل:** كانت هذه الخيارات **مكتوبة في كود الواجهة** (`CAT_INFO` في `ServicesPage.tsx`):

```ts
pharmacies: { group: 'region',    groupTitle: 'المناطق' }
doctors:    { group: 'specialty', groupTitle: 'الاختصاصات' }
transport:  { group: 'meta', metaKey: 'vehicle' }   // يقرأ meta.vehicle وليس حقل القسم
```

فلم يستطع المدير تغييرها، وكان السرفيس يقرأ حقلاً قديماً (`meta.vehicle`) بينما بياناته الفعلية في حقل قسم «نوع المركبة» (`vehicle`).

### التصميم الجديد

| الطبقة | الوصف |
|---|---|
| **`filters`** (جديدة) | **مكتبة الفلاتر**: اسم + **مصدر بيانات** (`region` · `specialty` · `field`) + أيقونة |
| **`category_filters`** (جديدة) | **الإسناد**: أي فلتر يخدم أي قسم، وواحد منها **أساسي** (`is_primary`) |
| **البذرة التلقائية** | عند أول تشغيل تُبنى المكتبة وتُسنَد الفلاتر — **بلا أن يفقد المدير شيئاً** |
| **التجميع في الخادم** | `GET /api/services` يردّ `groups` محسوبة من **كل** الخدمات قبل ترقيم الصفحات |

**البذرة على بياناتك الحالية (تلقائية، مرة واحدة):**

| القسم | الفلتر الأساسي | المصدر |
|---|---|---|
| صيدليات بشرية · كازيات · المخابر | المناطق | جدول `regions` |
| عيادات أطباء | الاختصاص | جدول `specialties` |
| سرفيس واسعافية | نوع المركبة | حقل `vehicle` في القسم |

المكتبة تُنشئ أيضاً فلتر **«اتجاه السفر»** من حقل `direction` (جاهز للاستخدام، غير مُسنَد).
البذرة **غير مدمِّرة**: لا تعمل إن كان المدير قد أنشأ فلاتر.

### لماذا الحساب في الخادم لا في الواجهة

كانت العدّادات تُبنى في الواجهة من الخدمات المحمّلة، فإن تجاوز القسم سقف الشريحة
نقصت العدّادات. الآن `groups` تُحسب من **مجموع** الخدمات المُرشَّحة قبل `array_slice`،
واختيار بطاقة يُصفّي محلياً — فتبقى بقية البطاقات ظاهرة بأرقامها الصحيحة.
كذلك **لم يعد** اختيار منطقة يُصفّر عدّادات باقي المناطق.

### ما بُني

**الخلفية (`api.php` · `includes/db.php` · `install.php`):**
- جدولا `filters` و`category_filters` + فهرسان، وترقية تقدّمية على قاعدة قائمة
- `group_services_by_filter()` — تجميع موحّد للأنواع الثلاثة، والخدمة التي ينقصها
  الحقل تذهب إلى «غير محدد» **بدل أن تختفي** فلا تصير خدمات لا يمكن الوصول إليها
- `GET/POST/PUT/DELETE /api/admin/filters` · `PUT /api/admin/categories/{id}/filters`
- `category_filters_map()` تُرفق الفلاتر بكل قسم في `/api/meta`

**الواجهة:**
- `lib/grouping.ts` (جديد) — محرّك الفلاتر: الأساسي، الثانوي، مطابقة الخدمة بالبطاقة.
  منهج مستقل يصلح لإعادة استخدامه في تطبيق أندرويد
- `ServicesPage.tsx` — تقرأ الفلتر الأساسي من القسم وترسم بطاقاته، بلا أي `CAT_INFO.group`
- **تبويب «الفلاتر»** في لوحة التحكم — مكتبة الفلاتر + جدول إسناد الأقسام بنافذة
  اختيار (☑ مُسنَد · ◉ أساسي)، وتحذير عند الحذف يذكر عدد الأقسام المتأثرة
- الفلاتر الإضافية (إن أُسنِد أكثر من واحد) تظهر **قائمة اختيار مصغّرة** داخل شريط
  الصفحة — وليست شريطاً أعلى الصفحة

### ١٠.١ إصلاحات ظهرت بعد الرفع — «المخابر» كانت صفحة صامتة

**الشكوى:** «جميع الأقسام تعمل بنجاح لكن قسم المخابر لم يعد يظهر فيه أي فلتر أو رسالة أنه لا يوجد بيانات، وقسم المخابر تم إنشاؤه مؤخراً ولم يكن موجوداً سابقاً».

**السبب — لم يكن في قاعدة البيانات ولا في الخدمات:** كان الخلل في **مطابقة الرابط بالرمز**.

| | القيمة |
|---|---|
| رمز القسم (`slug`) | `laboratory` |
| مساره (`route`) | `/laboratories` |
| الرابط الذي يفتحه الزائر | `/laboratories` ← يُبنى من `route` |

صفحة القسم كانت تبحث بالرمز وحده (`categories.find(c => c.slug === slug)`)، فالرابط `/laboratories` لا يطابق `laboratory` → **القسم غير معروف** → لا فلتر ولا بطاقات ولا رسالة. (وكانت الخدمة موجودة فعلاً: «مخبر النور» في ابوحمام.)

**الإصلاح:**

1. `findCategory(categories, slugOrPath)` في `lib/utils.ts` — تبحث بالرمز أولاً ثم بالمسار. **كلا الرابطين يعمل الآن** (`/laboratory` و`/laboratories`).
2. رسالة صريحة **«القسم غير موجود»** بدل الصفحة الفارغة الصامتة.
3. `buildGroups(items, filter)` في `lib/grouping.ts` — تجميع محلي احتياطي: إن لم يرسل الخادم `groups` (حزمة واجهة أحدث من الخادم) تُبنى البطاقات من الخدمات نفسها، فلا تظهر صفحة بلا بطاقات.
4. **ثلاث رسائل فراغ متمايزة** في `ServicesPage.tsx`: «لا توجد نتائج مطابقة» (الفلاتر حجبت + زر «إلغاء كل الفلاتر») · «لا توجد خدمات بعد» (القسم فارغ) · «القسم غير موجود» (رابط خاطئ).
5. **قسم جديد كان يُنشأ بلا أي فلتر** → خدماته تُعرض بلا بطاقات. الآن `attach_default_filter()` في `api.php` يُسنِد **«المناطق»** تلقائياً عند إنشاء أي قسم (يُطبَّق على **الإنشاء فقط**، فلا يُلغي قرار مدير ألغى فلاتر قسمٍ عن قصد).
6. في لوحة التحكم: **معاينة الرابط** تحت حقل «المسار» + تنبيه إن اختلف عن الرمز — حتى لا يتكرّر الالتباس.

**التحقق** (بمتصفح افتراضي على الحزمة المفكوكة):

| الفحص | النتيجة |
|---|---|
| `/laboratories` (المسار الحقيقي): العنوان + فلتر «المناطق» + بطاقة ابوحمام + الاختيار يعرض المخبر | ✅ ١٦/١٦ |
| `/laboratory` (بالرمز) يعمل أيضاً | ✅ |
| رابط غير موجود → «القسم غير موجود» | ✅ |
| قسم بلا فلتر · قسم بلا خدمات · فلاتر تحجب النتائج (+ زر الإلغاء) | ✅ ١٥/١٥ |
| الأقسام الأربعة الأخرى لم تتأثر · صفر أخطاء تشغيل | ✅ |

### ١٠.٢ إصلاحان إضافيان ظهرا أثناء الفحص النهائي

**(أ) نتيجة مُفلترة تُعرض كاملة.** في فرع «قسم بلا فلتر مُسنَد» كان القالب يعرض `items`

الزائر قد يُتجاهَل في هذا الفرع. أُصلح، وأُضيفت له رسالة «لا توجد نتائج مطابقة»

فلا تنطبق عليها قاعدة «غير المحدد آخراً». وُحِّدت المفاتيح (`*-none`) في مساري
الفلاتر والاحتياط معاً، وتُوحّدت التسمية مع الخادم («غير محدد» لا «غير محددة»).

## 📱 ١١. الفلاتر في تطبيق أندرويد

**الطلب:** «الآن يجب تطبيق التعديلات على تطبيق أندرويد».

**الوضع قبل:** التطبيق كان **يُثبّت** التجميع في كود Dart (`SectionConfig` في `lib/config/constants.dart`):

```dart
'pharmacies': … groupBy: 'region'
'doctors':    … groupBy: 'specialty'
'transport':  … groupBy: 'meta', metaKey: 'vehicle'
fallback(slug) → groupBy: 'region'     // أي قسم جديد = مناطق
```

فلا يعرف التطبيق شيئاً عن الفلاتر التي يُنشئها المدير ولا عن `is_primary`.

### ما نُفِّذ

| الملف | التغيير |
|---|---|
| `lib/models/models.dart` | نموذج **`CategoryFilterLink`** (`key` · `label` · `source_type` · `source_key` · `icon` · `is_primary`) + **`Category.filters[]`** يُقرأ من `/api/meta` + `primaryFilter` و`secondaryFilters`. `toJson` يكتبها كنص JSON للتخزين المحلي |
| `lib/services/database_service.dart` | ترقية القاعدة **٣ → ٤**: عمود `filters` في جدول `categories` + قراءته عند العمل بلا إنترنت (نص تالف ⇒ «بلا فلاتر» بلا انهيار) |
| `lib/screens/section_screen.dart` | **التجميع يتبع الفلتر الأساسي المُسنَد**: `_valueOf` (منطقة · اختصاص · **أي حقل** من `meta`/`fields`) · `_keyOf` · `_labelOf` · `_specialtyLabel` · `_groupIcon` (أيقونة الفلتر التي اختارها المدير) · `_buildGroups` بعدّاد «تعمل الآن» وترتيب مطابق للخادم · **صف الفلاتر الثانوية** بورقة اختيار سفلية (يظهر فقط إن أسنَد المدير أكثر من فلتر) · `_passes` منطق تصفية موحّد للقائمة والبطاقات |

| `test/category_filters_test.dart` | **١٣ اختباراً**: قراءة الفلاتر · حكم الأساسي على التجميع (مناطق · اختصاص · حقل) · «غير محدد» · التوافق الخلفي · **والفلاتر الثانوية (٤ اختبارات)** |

**التوافق الخلفي مضمون:** إن لم يُسنَد للقسم أي فلتر (خادم قديم) يرجع التطبيق إلى `SectionConfig` المضمّن كما كان — بلا أي تراجع.

**ثلاثة تفاصيل انتبهت لها بعد المراجعة:**

1. **الفلتر الثانوي كان يحجب خياراته.** كانت خيارات فلتر ثانوي تُبنى بعد تطبيق **كل** الفلاتر — وهو نفسه؛ فبعد اختيار «باص» تبقى «باص» وحدها في القائمة فلا يمكن التبديل إلى «إسعاف» إلا بإلغاء الفلتر أولاً. الآن يُبنى خيار كل فلتر من الخدمات التي تجتاز **بقية** الفلاتر فقط (`_passes(..., ignoreSecondary:)`) — وهو ما يفعله الويب (يستعمل تجميع الخادم الكامل).
2. **القسم صار «حيّاً».** كانت الشاشة تحتفظ بصورة القسم التي وصلت معها، فلو غيّر المدير فلتر قسم وهو مفتوح في التطبيق لما تغيّر شيء حتى إعادة التشغيل. الآن تُقرأ أحدث نسخة من مزوّد البيانات عند كل بناء (`_cat`).
3. **زر التحديث يعيد جلب الفلاتر أيضاً.** `_load(force: true)` كان يجلب **الخدمات** فقط؛ الآن يستدعي `app.sync()` أولاً فيُعاد جلب `/api/meta` بالفلاتر. أي أن تعديلاتك في اللوحة تظهر عند «تحديث» في التطبيق مباشرة.

**لماذا التجميع في التطبيق لا من `groups` الخادم؟** التطبيق يعمل **بلا إنترنت** من قاعدة محلية؛ فتجميع محلي بنفس قواعد الخادم يُبقي البطاقات والعدّادات صحيحة دائماً. القواعد نُقلت حرفياً وقُورنت بالخادم (أدناه).

## 📱 ١٤. تحديث تطبيق أندرويد — من داخل التطبيق

### ما طُلب

«وقت في نسخة APK حديثة تظهر رسالة في تطبيق أندرويد أنه في تحديث جديد، ويكون زر
تنزيل من داخل التطبيق مع شريط نسبة التحميل وسرعة التنزيل، وعند انتهاء التنزيل
يظهر زر تثبيت.»

### ما نُفِّذ — ثلاث قطع متكاملة

| # | القطعة | التفصيل |
|---|---|---|
| ١ | **الخادم** | `api/includes/app_update.php` (جديد) + `GET /api/app-update` عامة |
| ٢ | **لوحة التحكم** | تبويب «تحديث التطبيق»: رقم النسخة · **مسار الملف** · رفع · فحص مجلد · رابط خارجي · ملاحظات · إلزامي |
| ٣ | **التطبيق** | بطاقة في «حسابي»: تنبيه + تنزيل بنسبة وسرعة + زر تثبيت |

### الخادم — بلا مكتبات

`api/storage` مُحمّى، فمجلد `apk/` في جذر الموقع هو المستودع. عند رفع أي ملف APK
يقرأ الخادم **الإصدار من داخل الملف نفسه**:

- **قارئ ZIP** مكتوب بـPHP خالص (`apk_zip_entry`) — قراءة دليل المركز و فكّ
  deflate. لماذا؟ لأن استضافة المستخدم قد تكون بلا امتداد `zip` — فلا نعتمد عليه.
- **قارئ AndroidManifest الثنائي** (`apk_axml_manifest`) — يفكّ `resXMLTree`:
  جدول النصوص · خريطة المراجع · عنصر `manifest` وخصائصه. يستخرج `package` و
  `versionCode` و `versionName`، ويميّز الإحالة للمورد (TYPE_REFERENCE) عن النص.

**التحقق:** قورن القارئ بمحلّل مستقل (`androguard` في بايثون) على **٣١ ملف APK
حقيقي** (منها ملف ١٦ ميغا بـprotected chunks) → تطابق تام **28/28** بعد توحيد
تمثيل «غير موجود» (ملفاتان فشل عليهما المحلّل المستقل نفسه).

### اللوحة

تبويب جديد فيه: حالة النشر (الإصدار · الكود · الحجم · البصمة · الرابط) ·
**حقل «مسار الملف»** · رفع مع شريط تقدّم · «فحص مجلد apk/» · ربط ملف بعينه ·
حذف الملف المنشور · ملاحظات «ما الجديد» · مفتاح الإلزامي · رابط خارجي.

#### «مسار الملف» — المدير يحدّد مصدر التنزيل

حقل واحد يقبل: مساراً داخل الموقع (`apk/dalel-1.2.0.apk` · `dalel-1.2.0.apk`
في الجذر · مجلد فرعي) أو رابطاً كاملاً (`https://…`). واللوحة تعرض فوراً
ما وجده الخادم: وجود الملف · حجمه · **الإصدار المقروء من داخله** · رابط التنزيل.

- **حماية:** `..` مرفوض · الامتداد يجب أن يكون `.apk` · الملف المحلول يجب أن
  يكون داخل مجلد الموقع (مع فحص الروابط الرمزية عبر `realpath`).
- **تنبيه التخالف:** إن خالف رقم البناء الذي أدخله المدير الرقمَ داخل الملف،
  يظهر تحذير صريح قبل النشر (وإلا ظنّ الزبائن أنهم محدَّثون).
- **لا تحديث معطوب:** مسار بملف غير موجود ⇒ `available: false`، فلا يُعرض
  للتطبيقات زر تنزيل يقود إلى 404.
- الرفع والفحص يُملآن هذا الحقل تلقائياً — فيبقى المسار هو المصدر الواحد.

**حماية من التراجع:** إن كان الملف في المجلد إصداره أقدم من المنشور، يُربط
الملف لكن **لا يُنزل رقم الإصدار** — وإلا صار الزبائن «محدَّثين» وأُغلق أمامهم
التحديث الحقيقي.

## ⚙️ ١٥. بناء APK بضغطة — سير عمل على GitHub Actions

**الطلب:** «أنشئ workflow على المستودع لبناء APK، وعند أي تحديث أطلبه فيكون
جاهزاً وسريعاً».

**النتيجة:** `.github/workflows/build-apk.yml` — تفتح Actions ← «بناء APK» ←
**Run workflow**، وبعد نحو ٥ دقائق تجد ملف APK جاهزاً للتنزيل. بلا Flutter ولا
Android Studio على جهازك. الدليل الكامل: **[دليل-بناء-APK.md](دليل-بناء-APK.md)**.

### أخطاء حقيقية كشفها السير في أول تشغيل — وأُصلحت

1. **`Category.fromJson` كان ينهار بلا إنترنت.** حقل `filters` يُخزَّن في
   القاعدة المحلية **نصّاً** (`jsonEncode`)، لكن القراءة كانت
   `as List? ?? []` ⇒ `type 'String' is not a subtype of type 'List'` عند
   فتح أي قسم من القاعدة المحلية. و`features` و`meta` كانتا تعودان فارغتين
   **بصمت** (فقدان بيانات بلا رسالة). الآن `_l()` و`_m()` تفكّان النص أيضاً.
2. **`_upgrade` كانت تُنفّذ مراحل أحدث من المطلوب.** الشرط `oldV < N` وحده،
   فترقية `(2 → 3)` تشغّل مرحلة «حتى ٤» فتلمس جدولاً غير موجود. صارت كل مرحلة
   مقيّدة بـ`oldV < N && newV >= N`.
3. **فهرس على جدول مفقود.** `CREATE INDEX idx_services_zone ON services(...)`
   ينهار إن لم يكن الجدول قد أُنشئ ← `_indexIfTable` تتحقّق من `sqlite_master`.
4. **`AppTheme.dangerBg` غير موجود** في `update_card.dart` — كان يمنع
   `flutter analyze` و`flutter build`. صار `closedBg`.
5. **اختبارات القاعدة كانت تتشارك `:memory:`** — في `sqflite_common_ffi`
   هي قاعدة **مشتركة** (`file::memory:?cache=shared`)، فتتلوّث الاختبارات
   ببعضها وتعطي أعطالاً تعتمد على الترتيب. صارت ملفات مؤقتة فريدة، وأُضيف
   `DatabaseService.resetForTests()` لتفريغ القاعدة المؤجّلة.
6. **اختباران للفلتر الثانوي بتوقّعات خاطئة:** أحدهما كان يطلب ظهور «س٢»
   (في بطاقة «إسعاف») داخل بطاقة «باص» المفتوحة، والآخر ينقر على شريحة
   خرجت من عرض الشاشة (`ensureVisible`)، وآخر يطابق نص «الكل» في مكانين
   (`widgetWithText(ListTile, 'الكل')`).

**النتيجة النهائية على CI:** `الفحص والاختبارات ✅ success` ·
`بناء الحزمة ✅ success` · **٧٨ اختباراً** · artifact `dalel-apk-1.2.0-3`
بحجم **٢٦ ميغا**.

### توقيع الإصدار بمفتاح حقيقي + تحقق مرئي

- **المفتاح:** وُلّد مفتاح إصدار حقيقي — RSA **4096** بت · SHA256withRSA ·
  صيغة **PKCS12** · الاسم المستعار `dalel` · صالح حتى **فبراير ٢٠٥٤**
  (Google Play يشترط ما بعد ٢٠٣٣). بصمة الشهادة SHA-256:
  `CA:EE:71:6C:FB:1E:…:36:7C`.
- **لماذا PKCS12؟** صيغة `keytool` الحديثة وAndroid Studio، و`storeType`
  صار **مصرَّحاً به** في Gradle لأن الافتراضي يختلف بين إصدارات Java/Gradle
  فالملف بصيغة أخرى يفشل بـ«Invalid keystore format».
- **لا يُولَّد المفتاح في CI:** المستودع **عام**، وأي artifact متاح لمن
  يملك حساباً ≠ مالكه — فكان المفتاح سيتسرّب لحظة إنشائه.
- **خطوة تحقق جديدة في السير:** `apksigner verify --print-certs` تطبع بصمة
  الشهادة التي وقّعت الملف فعلاً وتُعلن «مفتاح إصدار ✅» أو «مفاتيح تصحيح ⚠️»
  ⇒ التوقيع صار **قابلاً للتأكد** لا للافتراض، وهو شرط النشر على Play.
- **حماية:** `.gitignore` يستبعد مجلد `signing/` كاملاً.

### نسخة 64 بت + اختيار المعمارية

مدخل جديد `arch` (**الافتراضي `arm64`** — نسخة 64 بت كما طُلب):

| القيمة | ما يُبنى | اسم الملف |
|---|---|---|
| `arm64` (افتراضي) | `--target-platform android-arm64` | `dalel-1.2.0-3-arm64.apk` |
| `universal` | بلا علم (كل المعماريات) | `dalel-1.2.0-3-universal.apk` |
| `arm32` | `android-arm` | `…-arm32.apk` |
| `x64` | `android-x64` | `…-x64.apk` |

اختيار ملف المخرَج يتبع المعمارية (`app-arm64-v8a-release.apk`) مع احتياط
يمنع الفشل لو تغيّر الاسم في إصدار Flutter آخر.

**القياس على CI:** نسخة 64 بت = **١٠٫٣ ميغا** مقابل ٢٦ ميغا للموحّدة —
أي أقل من نصف الحجم، وهو الفرق الذي يوفّره حذف معماريتَي 32-bit وx86.

### مرافق

- `DALEL_BASE_URL` عبر `--dart-define`: نسخة تخاطب `/daleltest` أو `/dalel`
  بلا تعديل كود (الافتراضي الآن: الحيّ `/daleltest`).
- توقيع إصدار حقيقي من `android/key.properties` مع ارتداد آمن إلى مفاتيح
  التصحيح.
- `.gitignore` يستبعد `key.properties` و`*.jks` و`*.keystore`.
- تحقق مبكّر من صيغة المدخلات برسائل عربية واضحة، وأسطر الفشل تُعلَن
  كتعليقات في واجهة Actions بدل الدفن في سجل طويل.
